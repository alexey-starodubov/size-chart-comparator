# Приёмка 220 · size-chart-comparator

## Как повторить проверки

```bash
npm ci
npm run typecheck
npm test                 # 19 юнит-тестов (Vitest)
npm run e2e:install      # один раз: Chromium для Playwright
npm run e2e              # 18 сквозных тестов по dist/ (вложенный путь и корень)
npm run build && npm run e2e
```

Замер раунда 4 печатается строкой `PERF220 {...}` в выводе `npx playwright test e2e/perf.spec.ts`.

## Окружение проверки

Linux (облачная песочница), 2 ядра. Node.js 22.23.5 / npm 10.9.9. React 19.3.1, Vite 8.3.8, TypeScript 7.0.2, Vitest 5.1.1, Playwright 1.65.1 (Chromium headless shell). Локаль Playwright `ru-RU`, часовой пояс `Europe/Moscow`.

## Раунд 1. Правила и полнота продукта

Сверка с ТЗ: сущности поставщик, модель, размер, тип замера, значение, единица; см и дюймы к единой шкале с заданным округлением; пропуск показывается отдельно; превышение порога подсвечивается; экспорт CSV и печатная таблица; сравниваются только одинаковые тип и способ; целые мм, максимальный разброс по группе, строгое превышение; отсутствующие поля не участвуют; модули `chart-editor`, `unit-conversion`, `measurement-compare`, `chart-export`; явные подписи единицы и формата; неоднозначные строки выводятся для исправления; приёмка M 48/52 см при пороге 2 см и «нет данных» при загрузке недостающего замера.

| Проверка или находка | Результат |
|---|---|
| Тесты ловят снятие защиты: «больше порога» заменил на «не меньше» | падают 3 теста (ровно на пороге и др.) |
| То же: отключил приведение кириллических букв в размере | падают 4 теста (кириллическая «М», демо, CSV) |
| То же: отключил поиск конфликтов | падают 3 теста |
| Перевод в мм | дробная арифметика без плавающей точки: 10,3 см → 103 мм, 19 1/2″ → 495, 1/4″ → 6; ровно 0,5 мм при «до ближайшего» → 1, при «вниз» → ошибка «После округления получается 0 мм» |
| Две строки одного поставщика на одну ячейку через разные названия («Ширина груди» и «Грудь ПО» → Грудь, по плоскости) | тоже конфликт: иначе одно значение молча перезаписало бы другое |
| **Дефект**: у неверного значения под полем было «используйте 48, 48,5 или 19 1/2» без начала фразы «Не число:» — интерфейс резал текст неоднозначности по «: » | у неоднозначности отдельное поле `message`, под полем — полная фраза (e2e) |
| Ошибки моих тестов: неверное число строк у поставщика в ожидании (13 вместо 11), ожидание CSV без кавычек вокруг ячейки с кавычками | исправлены ожидания, код верен |

## Раунд 3. Удобство и доступность

Просмотр снимков 1200×1000 и 360×800: замеры, сопоставление, сравнение, карточка товара.

| Находка | Исправление | Повторная проверка |
|---|---|---|
| На 360 px таблица сравнения уходила в горизонтальную прокрутку внутри блока: страница не прокручивалась, но разброс и «больше порога» были за краем экрана. Обычная проверка ширины страницы этого не видела | на узком экране строка сравнения и таблица для карточки — карточкой с подписью у каждой ячейки («Хлопок-Юг, см 52,0», «Разброс, см 4,0 — больше порога») | e2e 360/320 проверяет и прокрутку внутри таблиц |
| Строки редактора на узком экране — четыре поля подряд без подписей | подпись столбца у каждого поля | снимок, e2e |
| На «Сопоставлении» выпадающие списки растягивались на всю ширину и стояли столбиком | ширина по содержимому | снимок |
| Поле «Модель» в новой строке обрезало «Футболка базо…», список «Округление» — «до ближайшего» | поля шире | снимок |
| Подсветка только цветом | в ячейке разброса текст «— больше порога», жирным | e2e |

Клавиатура: «Новый поставщик» → Enter; строка заполняется Tab, Enter добавляет и возвращает фокус в «Размер», модель, замер и единица сохраняются для следующего размера. Ошибка — у поля, с `aria-invalid` и фокусом.

## Раунд 4. Производительность и качество реализации

Данные: 8 поставщиков × 150 моделей × 6 размеров × 5 замеров = 36 000 строк, два поставщика в дюймах, каждая 50-я строка без значения, каждая 400-я с ошибкой (90 неоднозначных). Chromium headless, `e2e/perf.spec.ts`.

| Действие | До | После кэшей | После отложенного анализа |
|---|---|---|---|
| Ввод в поле значения (10 изменений, медиана / максимум) | 258 / 340 мс | 84 / 126 мс | **18 / 29 мс** |
| Открытие файла проекта до таблицы сравнения | 388 мс | 286 мс | 224 мс |
| Смена модели в сравнении | 86 мс | 71 мс | 50 мс |
| Ввод порога до новой сводки | 422 мс | 171 мс | 397 мс (из них 250 мс ожидания паузы ввода) |
| Открытие «Замеров» (100 строк из 4 500) / «Сопоставления» (90 неоднозначных) | 130 / 167 мс | 96 / 94 мс | 118 / 78 мс |

| Находка | Исправление |
|---|---|
| Каждая буква в поле значения пересчитывала анализ всех 36 000 строк и держала ввод 258 мс | кэш нормализации названий и размеров и перевода значений (повторяются тысячи раз), ключи считаются один раз на строку; анализ без кэшей — ~100 мс, с прогретыми — ~50 мс |
| Даже 50 мс на каждую букву заметны | на проектах от 5 000 строк ввод текста пересчитывает анализ через 250 мс после паузы, действия (загрузка, добавление и удаление строк, сопоставление, единицы) — сразу. Сводка показывает настройки, с которыми посчитан анализ, а не текущие поля, поэтому порог в подписи и счётчик не расходятся. Тест проверяет, что последнее введённое значение доходит до сравнения |

Цена решения: на больших проектах порог применяется через 250 мс после паузы ввода. На демо и проектах меньше 5 000 строк анализ сразу.

## Известные ограничения

- Нет импорта .xlsx и .csv-файлом: таблица вставляется текстом.
- Нет допусков поставщиков и порога для каждого типа отдельно.
- Печать проверена эмуляцией `print` в Chromium: реальный предпросмотр печати в разных браузерах не проверялся.
- Данные живут в одном браузере, перенос — файлом проекта.
